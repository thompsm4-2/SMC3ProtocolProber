## 2. SMC3 Communication

### 2.1 Motor Command Encoding and Addressing

**Source:** `src/calibration/h3_characterize.py`

**Frame Format (lines 197-201):**
```python
def smc3_frame(motor, position):
    if motor not in "ABC":
        raise ValueError(f"invalid motor: {motor!r}")
    position = max(MIN_POS, min(MAX_POS, int(position)))
    return bytes((91, ord(motor), (position >> 8) & 255, position & 255, 93))
```

- **Byte 0:** `0x5B` (91) - Start bracket `[`
- **Byte 1:** Motor identifier (65='A', 66='B', 67='C')
- **Bytes 2-3:** 16-bit position, big-endian
- **Byte 4:** `0x5D` (93) - End bracket `]`

**Example frames:**
- Center (512): `[A 02 00]` = bytes `[91, 65, 2, 0, 93]` (line 29)
- Offset +20: `[A 01 FE]` = bytes `[91, 65, 1, 254, 93]` (line 34)
- Position 532: `[C 02 14]` = bytes `[91, 67, 2, 20, 93]` (line 39)

**Position Range:**
- MIN_POS = 0 (line 39)
- MAX_POS = 1023 (line 40)
- CENTER = 512 (line 38)

def poll_due(self, motors, positions):
    now = time.monotonic()
    if now < self.next_poll:
        return
    for motor in motors:
        requested = positions["ABC".index(motor)]
        self.poll_motor(motor, requested)
    self.next_poll = time.monotonic() + self.interval

        requested = positions["ABC".index(motor)]
        self.poll_motor(motor, requested)
    self.next_poll = time.monotonic() + self.interval

- `poll_now()`: Polls immediately, overwrites next poll time

### 2.4 Response Format and Feedback/Target Extraction

**Source:** `src/calibration/h3_characterize.py`

**Classification (lines 204-214):**
```python
def classify_command(command):
    if command == b"[ver]":
        return "VERSION", "", None
    if command == b"[ena]":
        return "ENABLE", "", None
    if len(command) == 5 and command[1] in (ord("A"), ord("B"), ord("C")):
        return "POSITION", chr(command[1]), (command[2] << 8) | command[3]
    if command in READ_COMMANDS.values():
        motor = next(k for k, value in READ_COMMANDS.items() if value == command)
        return "READ", motor, None
    return "UNKNOWN", "", None
```

**Version Response (lines 252-260):**
```python
def request_version(ser, tx_logger=None):
    ser.reset_input_buffer()
    send_command(ser, b"[ver]", tx_logger)
    response = ser.read(5)
    if len(response) == 5 and response[0] == 91 and response[1] == ord("v"):
        value = (response[2] << 8) | response[3]
        print(f"SMC3 version: {value / 100:.2f}  raw={response!r}")
    else:
        print(f"SMC3 version response: {response!r}")
```

- Reads exactly 5 bytes after version request
- Parses version as 16-bit big-endian value divided by 100
- Example: `[ver]01005D` = version 1.00

**Readback Response Format:**
- Expected format: `[rda]OK5D` or similar (from test file lines 192-198)
- Pattern: `[rda]` + status + checksum
- **NOT IMPLEMENTED:** No extraction of actual position values from readback responses
- The poller logs responses as hex but does not parse position values

### 2.6 Serial Connection Sharing

**Source:** `src/calibration/h3_characterize.py`

**Single Serial Connection for H3:**
- Line 572: Opens one H3 serial connection
- Line 576-580: ReadbackPoller uses the SAME connection (`self.ser = ser`)
- Line 648-649: Main thread calls `readback_poller.poll_due()` during sweep

**Safety Analysis:**

**VERIFIED-SOURCE:** The implementation shares a single serial connection for both motor commands and readback polling.

**Potential Issues:**

1. **Line 643:** After sending motor command and settling:
   ```python
   if readback_poller is not None:
       readback_poller.poll_now(args.readback_motors, positions)
   ```

2. **Line 648-649:** During measurement:
   ```python
   while time.monotonic() < end_time:
       if readback_poller is not None:
           readback_poller.poll_due(args.readback_motors, positions)
       time.sleep(0.01)
   ```

**Problem:** The main thread writes motor commands while the ReadbackPoller may be reading responses. This creates a race condition where:
- Main thread writes a motor command
- ReadbackPoller reads what it thinks is a readback response
- The response bytes are discarded

**VERIFIED-DOCUMENTATION:** `docs/SOFTWARE_ARCHITECTURE.md` line 68:
> "Separate WT901C serial reader is acceptable because it is a different port."

This implies separate ports are preferred, but H3 uses a single port for both commands and readback.

### 3.4 Raw Frame Handling

**Source:** `src/calibration/h3_characterize.py`

**Buffer Management (lines 327-365):**
```python
def _run(self):
    while not self.stop_event.is_set():
        data = self.ser.read(128)
        if not data:
            continue
        self.buffer.extend(data)
        self._parse_buffer()

def _parse_buffer(self):
    while len(self.buffer) >= FRAME_LEN:
        try:
            start = self.buffer.index(0x55)
        except ValueError:
            self.buffer.clear()
            return
        if start:
            del self.buffer[:start]
        if len(self.buffer) < FRAME_LEN:
            return

        frame = bytes(self.buffer[:FRAME_LEN])
        decoded = decode_wit(frame)
        if decoded == "BAD_CHECKSUM":
            self.bad_checksums += 1
            del self.buffer[0]
            continue
        del self.buffer[:FRAME_LEN]
        if decoded is None:
            continue
        ...
```

**Buffer Behavior:**
- Reads 128 bytes at a time (line 329)
- Extends buffer with received data
- Searches for `0x55` start marker
- If marker not found, clears entire buffer (line 341-342)
- If marker found, deletes everything before it (line 343-344)
- Parses complete frames from buffer
- On BAD_CHECKSUM, deletes only first byte (line 351-352)
- On incomplete frame, returns without clearing (line 344-345)

**Malformed Frame Handling:**
- **Incomplete frame:** Buffer retained, returns to loop
- **BAD_CHECKSUM:** Buffer advances by 1 byte, increments counter
- **Unknown type:** Frame discarded (line 354-355)

## 8. Summary

### 8.1 Architecture Overview

**v0.4.1 Architecture:**
- Single Python file, linear execution
- One serial connection for H3 (commands + readback)
- Separate serial connection for WT901C
- Asynchronous WT901C reader thread
- Synchronous readback polling in main thread
- CSV output with 22 columns
- TX logging and readback logging

### 8.2 What v0.4.1 Provides

**Working Components:**
1. SMC3 frame encoding/decoding
2. Sweep sequence generation
3. Position calculation with bounds checking
4. TX logging with status tracking
5. WT901C packet parsing and decoding
6. Sample collection and CSV output
7. Analyzer compatibility

**Known Limitations:**
1. Serial contention between commands and readback
2. No readback position extraction
3. No timestamp synchronization
4. No point association
5. Readback polling rate limited to ~4 Hz per motor (default)

### 8.3 What v0.5 Must Add

**Critical:**
1. Separate serial connection for readback (or non-blocking reads)
2. Timestamp synchronization across all logs
3. Readback position extraction
4. Point association between commands and sensor samples

**Important:**
1. Serial error recovery/retry
2. Configurable WT901C sampling rate
3. Readback timing statistics

**Nice to Have:**
1. Asynchronous readback polling
2. Response timeout adjustment
3. Better malformed frame handling

### 8.4 Technical Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Serial contention | High | Use separate serial connection |
| Timestamp drift | Medium | Use synchronized clocks |
| Readback data loss | Medium | Non-blocking reads |
| Position extraction | Low | Parse response format |
| Point association | Medium | Add correlation logic |

### 8.5 Unresolved Questions

1. What is the actual format of SMC3 readback responses?
2. What is the WT901C default sampling rate?
3. Does serial contention cause data loss in practice?
4. Can readback polling run concurrently with motor commands safely?
5. What is the acceptable response latency for 0.25s interval?
6. How does the SMC3 controller handle rapid readback requests?
